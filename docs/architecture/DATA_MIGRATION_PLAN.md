## 3. 空库与已有库升级

### 空库

先确认这是操作者批准的正式路径/新建范围、父目录权限/备份与可用磁盘，不因为默认local.sqlite3不存在而建另一库。明确环境、journal政策和SQLite运行时能力，单独初始化已批准的连续迁移前缀（v1→目标）；事务失败不得留半个账本或业务表。仅批准v3时不得顺带安装v4–v8。

### 已有v1/v2库

1. 使用不触发initialize的只读检查器识别路径、文件身份、Schema/DDL/checksum、sidecar、引用完整性和数据计数；不把采集脚本参数当UI配置。v1先按原v2升级，再追加已批准前缀。
2. 明确停止/冻结所有写者与会自动initialize的UI/CLI；只禁采集按钮不够。计划停机和回滚窗口必须包括Windows进程、后台任务、共享root。先备份，再获得迁移写锁；锁/磁盘不足就失败退出，不能关闭完整性约束。
3. 在一个明确事务内执行新增DDL、完整性检查和迁移账本；维持原`BEGIN IMMEDIATE`/rollback语义，不在其中切journal或foreign_keys。SQLite允许单写者；并发写/SQLITE_BUSY有界等待后阻断，不无限重试。[SQLite事务说明](https://www.sqlite.org/lang_transaction.html)
4. 提交前检查新对象/索引/触发器、FK、原v1/v2指纹和已保存旧数据哈希不变；提交后以新版只读查询及模块烟测核验，才恢复经批准写者。

不得在原表增加NOT NULL列再填“未知正常值”；本方案所有扩展旁挂新表。旧Schema checksum与新表SQL分别核验，不更新旧账本使篡改变合法。

## 4. 目录回填与幂等

只回填现有数据的**索引和引用**，不是重新下载/重写行情。由显式清单固定旧表、主键、source/version、三/四时点、payload hash和库身份；每批上限建议1000行、单写短事务，实际锁时/内存验收后再调。不得扫描临时测试库并批量导入正式库。

- 先登记真实可证来源描述，许可/时点缺失保留UNKNOWN；不要制造历史许可或历史source_id注册时间。
- 按完整业务键/原版本校验，建立B04/B05；同映射同hash重跑返回DUPLICATE，不新增旧ingestion_run、不改变旧时间。不同hash立刻冲突，暂停回填。
- 旧DailyBar无observed，B04仍NULL；旧JSON available/ingested缺失仍NULL。今天建立目录只记registered_at，不可把它写入历史四时点。
- 公司行动、名称、ST、停牌、行业没有历史来源则不回填。当前快照不能生成过去每日版本。既有真实550行观察可先做来源/时点/文件缺口清单；是否导入需单独来源/路径授权。
- 文件与SQL非一个原子事务：先校验私有内容地址，后同事务登记整条目录及typed记录；孤儿文件待核对、不直接删；缺载荷阻断，不伪造内容补hash。

## 5. 备份与恢复（仅设计）

未来实施前记录：正式绝对路径、文件身份/大小、journal/sidecar、Schema版本和源码SHA、写者清单、备份目的绝对路径与权限、磁盘上限和恢复操作者。备份与恢复目的禁止使用猜测路径或正在运行的正式文件名。

使用SQLite Online Backup API对已确认源生成一致性副本，并将代码/配置/Schema及原始证据manifest一起登记到私有备份目录；不能只复制活动主文件忽略已提交WAL。[官方Backup说明](https://www.sqlite.org/backup.html)支持在线副本，但本方案仍在迁移窗口冻结写者，使备份基线与迁移基线可明确对账。大证据载荷按内容地址另备，数据库备份不代表证据文件也已备份。

备份完成后在未来授权的隔离目录打开副本验证：`quick_check`、`integrity_check`、`foreign_key_check`、Schema/checksum/计数/版本链/载荷hash和代表查询。`integrity_check`不替代外键检查；具体断言与输出均归档。[PRAGMA说明](https://www.sqlite.org/pragma.html#foreign_key_check) 这些命令本轮没有执行，也不创建副本来演练。

恢复分三种：

| 情况 | 最小动作 |
| --- | --- |
| 事务提交前失败 | ROLLBACK本事务，保留原库和备份；核对账本/对象/旧记录恢复原样，失败证据保留，不以改checksum重试 |
| 已提交新Schema、尚未恢复业务写 | 禁止旧代码直接指向升级库；将成对旧代码和已验证备份恢复到**另一个明确批准路径**验收，人工切换绑定；不在活动文件上覆盖/删表“降级” |
| 新Schema已接受新数据 | 暂停写者，先保全新库与证据；优先修复后滚动前进。若必须回退，必须规划新增版本/结果的保全与重新导入/对账；不得自动恢复旧备份丢掉新数据 |

没有通用DROP新表回滚脚本。旧发布JSON的回滚只切数据发布指针，与SQLite恢复分离。备份保留/清理需要批准后的容量与引用策略，不在本设计任务操作。

## 6. 旧代码兼容：明确“不兼容自动启动”

main的`Database.initialize()`第107–109行检查`len(applied)>len(migrations)`并拒绝newer schema。故即使只新增表，旧v2应用仍不能启动升级后的v3库。不能关闭该校验、伪造账本长度或修改v1/v2 checksum作为兼容方案。

正式升级前须先交付且审查：

1. 新版迁移执行入口与业务只读打开入口分离；后者显式URI mode=ro/query_only，不执行initialize或journal改变；识别受支持Schema能力范围，不认识则明确拒绝。这是后续实现，不是当前已经有的功能。
2. 运行配置绑定数据库身份/绝对路径和能力版本；新代码只读取已安装模块；旧应用如必须继续运行，保持配套v2快照/原环境只读展示或消费独立JSON，不能同时偷偷写另一库构成双主。
3. 回滚准备成对代码+数据库版本，而非仅切代码symlink。EC2新结果viewer只读协议JSON，不升级云端现有v2库；其代码与本地事实Schema生命周期可独立。
